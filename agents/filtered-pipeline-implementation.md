# 독립 수집·필터 파이프라인 구현 기록

정리일: 2026-09-08

## 완료 범위

기존 draw를 수정하지 않고 공식 수집 클라이언트·달력을 선별 이전했다. 날짜·번호 검증, CSV 원자적 반입, 최신 당첨 이력 완전성 검사, 고정 필터1~4, 역대 당첨번호 동일 이동 제외, 통계 차이10·합계20 교집합, filtered-v1 선택과 생성 원장 metadata를 구현했다.

고정 후보·filter5·filter6는 한 벌씩 유지한다. 공용 DB 행 잠금과 transaction으로 수집·후보 교체·생성 저장을 직렬화하며 TRUNCATE를 사용하지 않는다. 정정 수집은 기존 후보를 무효화한다.

## 검증과 적용 대기

- 전체 8,145,060개 조합 미저장 순회: 고정 후보 6,524,309개 확인.
- 공식 최신 1240회(2026-09-05) 한 건 조회·파싱 성공, DB 미저장.
- 신규 migration MySQL --pretend: 테이블 5개·comment·인덱스·metadata 및 상태 초기 행 SQL 확인.
- 실제 개발 DB에는 아직 새 migration·초기 CSV·후보 적재를 적용하지 않았다.
- 수백만 행 실제 MySQL 적재 성능과 동시 프로세스 잠금 시험은 후속 확인 대상이다.
- 초기 반입 CSV 파일은 아직 제공되지 않았다. 운영 draw DB의 파일 내보내기는 이번에 실행하지 않았다.
- 최종 테스트 결과는 완료 응답과 실행 로그를 참고한다. 설계 원본은 docs/filtered-pipeline-design.md다.

최종 검증: SQLite 메모리 DB 테스트 16개, 단언 3,386개 통과. 실제 개발 MySQL 8.4.10에서 기존 생성 기록 0건과 InnoDB 엔진을 읽기 전용으로 확인했다. 실제 새 migration은 미적용이다.


## 승인된 Migration 적용

2026-09-08 사용자 확인 후 새 migration을 개발 DB에 적용했다. migrate:status 배치 2 / Ran, 신규 5개 테이블의 엔진·테이블 및 컬럼 comment, metadata nullable JSON을 읽기 전용 조회로 검증했다. 상태 초기 행은 1건, 나머지 업무 테이블은 모두 0건이다. 이력·후보 데이터 적재는 별도 확인 대상으로 남긴다. 앞선 미적용 기록은 이 결과로 대체한다.


## 초기 데이터 준비 완료 (2026-09-08)

사용자가 디스크 여유와 실제 적재 실행을 확인한 뒤 순서대로 적용했다. 대상은 개발 DB luckydive_generator_dev이며, 기존 draw 원본 DB는 변경하지 않았다.

| 데이터 | 정확한 검증 건수 |
| --- | ---: |
| winning_numbers | 1,240 |
| filtered_base_candidates | 6,524,309 |
| filter5_numbers | 6,513,955 |
| filter6_numbers | 1,027,946 |
| recommendation_runs | 0 |

상태 ready=1, 기준 회차 1240, 추천 대상 1241을 확인했다. 전체 당첨 이력 지문과 준비 지문이 일치하며, 모든 건수는 저장 없는 사전 계산과 같다. filtered-v1 5게임 CLI dry-run도 성공했다. 추천 결과 저장·외부 API 제출·자동 스케줄 등록은 실행하지 않았다.

MySQL information_schema의 데이터와 인덱스 크기 합계는 약 725.1MiB다. 이는 조회 시점의 테이블 크기이며 undo/redo·binlog·파일시스템 여유까지 포함하는 수치는 아니다. 서버 디스크 여유는 사용자 확인을 근거로 진행했다.

대량 적재는 MySQL 5,000행 단위(45,000 바인딩)로 처리하고 SQLite는 500행으로 유지했다. 처리 건수는 commit 전임을 표시한다. 묶음 조정 후 격리 테스트 16개/3,386단언 통과, 실제 MySQL 적재 및 최종 건수 검증 통과. 고정 후보 준비 완료 시각은 10:23:22, 최신 필터 준비 완료 시각은 10:39:16(한국 시간)이다. 여러 프로세스를 동시에 실행하는 부하 시험은 수행하지 않았다.

CSV와 사전/사후 JSON은 storage/app/private/initial-draws에 보존했다. 고정 후보는 이후 재사용하고, 새 당첨번호 수집 후 최신 필터만 다시 준비한다. 앞선 미적재·대기 상태 기록은 이 결과로 대체한다.


## 게임별 단건 조회 변경

사용자 요청에 따라 filtered-v1의 최종 선택을 게임별 난수 ID 추출 → 기본키 단건 조회의 반복으로 변경했다. 기존 whereIn 일괄 조회는 제거했다. 동일 실행의 중복 게임 제외, 전체 수량 미확보 시 실패, 최신 후보 검증과 transaction 잠금은 유지한다. 필터 규칙과 선택 확률은 동일해 버전은 유지하며 조회 방식 변경만으로 번호 분산이 개선된다고 보장하지 않는다. 후보 재적재와 실제 DB 변경은 필요하지 않다.


## DB 난수 정렬로 최종 선택 변경

사용자 요청에 따라 앞선 게임별 random_int·단건 조회를 MySQL ORDER BY RAND() LIMIT 요청 게임 수의 단일 조회로 교체했다. Laravel inRandomOrder()로 DB별 난수 함수를 사용한다. 전체 후보 수와 요청 수량을 구분하고, 수량 부족 시 부분 결과 저장 없이 실패한다. 최신 이력 검증·transaction·버전은 유지한다. 기존 단건 조회 설명보다 이 변경이 우선한다. 후보 재적재나 migration은 필요하지 않다.

## DB 난수 정렬의 게임별 조회 변경

사용자 요청에 따라 최종 선택을 ORDER BY RAND() LIMIT 1의 반복으로 변경했다. 5게임이면 5회 선택하며 이미 선택한 ID를 NOT IN으로 제외한다. 앞선 단일 조회 설명보다 이 변경이 우선한다. 개별 번호 겹침은 허용하고 동일 조합만 중복 제외한다. 최신 이력 검증·transaction·전체 수량 확보·알고리즘 버전은 유지한다. 각 조회의 난수 정렬 비용은 반복되며, 분할 조회가 번호의 다양성을 보장하지는 않는다. 실제 DB 변경은 필요하지 않다.

## 최초 선택 방식 복원

수동 비교를 위한 사용자 요청으로 random_int로 서로 다른 후보 ID를 추출한 뒤 WHERE IN으로 일괄 조회하는 최초 방식을 복원했다. 게임 반환 순서는 난수 추출 순서를 유지한다. 앞선 SQL RAND 및 게임별 조회 설명보다 이 기록이 우선한다. 최신 후보 검증과 전체 수량 확보 조건은 유지하고 실제 DB 변경 없이 적용한다. 수동 확인은 `./scripts/docker.sh local run --rm app php artisan lotto:generate --algorithm=filtered-v1 --count=5 --dry-run`으로 실행한다.
